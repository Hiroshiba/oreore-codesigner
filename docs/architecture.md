# 構成と信頼境界

このリポジトリは、個人用 Electron アプリの自己署名証明書と公開権限を一か所で管理します。
アプリごとのリポジトリへ署名用秘密鍵を置かず、中央で許可したアプリだけを公開します。
ソースのビルドスクリプトを実行する環境と、秘密鍵や公開権限を扱う環境を分離することが目的です。

## ジョブの責務

| 段階                 | 入力と処理                                                                 | 使用できる権限                      |
| -------------------- | -------------------------------------------------------------------------- | ----------------------------------- |
| 設定検証とソース取得 | `app_id` で登録内容を選び、`tag` をコミット SHA に固定してソースを取得する | 対象リポジトリ一つの Contents read  |
| OS ごとのビルド      | 固定したソースから、署名前のアプリ本体を作る                               | 署名鍵と公開トークンを渡さない      |
| OS ごとの署名と梱包  | 成果物を検査し、アプリ本体へ署名した後、配布形式へ梱包する                 | その OS の署名鍵                    |
| Release set の検証   | ファイル、更新メタデータ、ハッシュ、対象バージョンの対応を確認する         | 署名鍵と公開トークンを渡さない      |
| 公開                 | 検証済み成果物を既存 Release へ追加する                                    | 対象リポジトリ一つの Contents write |

取得時のタグ名と、実際にビルドするコミットは別々に記録します。
タグを移動できる rolling release でも、ひとつの実行中は取得時に確定した SHA のソースを使います。
中央設定とワークフローは保護されたブランチで管理し、アプリ側のソースから取得先、署名コマンド、公開先を変更できないようにします。
GitHub Actions はバージョンタグではなくコミット SHA に固定します。

ソースのビルドはアプリが管理するコードを実行するため、信頼境界の外側として扱います。
署名ジョブはビルド成果物を受け取り、中央が管理する処理で署名します。
`electron-builder --prepackaged` はアプリ本体を署名しないため、梱包前に本体と内部の実行可能コードへ署名します。
公開ジョブだけが公開用トークンを持ちます。

## 成果物と更新

| OS      | 初回導入                        | 自動更新                   | 維持する識別情報                |
| ------- | ------------------------------- | -------------------------- | ------------------------------- |
| macOS   | DMG                             | ZIP と更新メタデータ       | bundle ID、署名証明書、秘密鍵   |
| Windows | WebSetup とそのダウンロード対象 | 通常 NSIS と更新メタデータ | appId、NSIS GUID、publisherName |

Windows の更新メタデータは通常 NSIS を指します。
アプリ側では `disableWebInstaller=true` を設定し、更新経路へ WebSetup を混在させません。
blockmap は対応する成果物とともに公開します。
差分更新の可否は配布形式や更新ライブラリの動作にも依存するため、全量ダウンロードへの切り替えを実機で確認します。

Release set は、同じソースとバージョンから作った配布ファイル、blockmap、更新メタデータの一式です。
検証に通った一式だけを公開します。
配布ファイルを先に公開し、それらを参照する更新メタデータを最後に公開します。
この順序でも GitHub Release への公開全体が原子的になるわけではありません。

正式版の公開は追加のみです。
同名で異なる内容の既存 asset がある場合は停止します。
同名で digest が一致する asset は再アップロードしません。
rolling development release に限り、中央設定で置換を許可し、実行時にも `replace_existing_assets=true` を指定した場合だけ置換します。
置換は既存 asset の削除と新しい asset のアップロードに分かれ、自動ロールバックは行いません。
Immutable Release の asset は変更できません。

## 対象外

Apple の Developer ID、notarization、公的な Windows コード署名証明書の取得は、この構成に含みません。
自己署名だけで Gatekeeper の標準許可を得ることや、SmartScreen の警告を必ず消すこともできません。
Smart App Control の強制環境で自己署名アプリを使うことは対象外です。

端末での証明書確認と初回起動の許可は、利用者本人が行います。
証明書を追加しただけで、任意のアプリが OS の保護機能を通過できるとは扱いません。
macOS の `com.apple.systempolicy.rule` を使う構成プロファイルは実験に分離し、標準導入の前提にしません。
